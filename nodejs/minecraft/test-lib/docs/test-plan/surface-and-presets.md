# Test plan — surface and presets

Wave-1 plan for the `surface-codegen`, `guard-data`, `error-model`, `world-and-dimensions`,
`presets` and `package-and-exports` areas. Every case below is a planned vitest `it`, with what it
asserts and the spec sentence or fact/decision it comes from. No tests are written yet.

## Files and conventions

Tests are colocated `src/*.test.ts`. The generated classes live under `src/generated/**`, which is
gitignored, so their tests live beside the hand-written sources rather than next to them.

| file                        | sections         |
| --------------------------- | ---------------- |
| `src/create-server.test.ts` | A, B, C          |
| `src/world.test.ts`         | D                |
| `src/presets.test.ts`       | E, F             |
| `src/shape.test.ts`         | G                |
| `src/arity.test.ts`         | H                |
| `src/guard.test.ts`         | I                |
| `src/errors.test.ts`        | J                |
| `src/read-order.test.ts`    | K                |
| `src/package.test.ts`       | L                |
| `src/types.test.ts`         | M (compile-time) |

Conventions used throughout:

- A test reaches a fake only through the public entry point (`createServer`, `createEntity`,
  `invalidate`, `withVanillaDimensions`, …), except where a case explicitly probes generated
  internals (section G) or the guard data file (section I).
- Calls that deliberately break arity or types go through a single local helper
  `const loosely = (o: unknown) => o as Record<string, (...args: unknown[]) => unknown>`, so the
  wrong-arity probes do not need `@ts-expect-error` on every line.
- Message assertions are exact-string (`toThrowError` with a string, or
  `expect(err.message).toBe(…)`), never a substring, because the messages are the engine's own.

**Cross-area dependencies.** Sections F, G, H, I and K need `createEntity` / `invalidate`
(`entity-model`), and I additionally needs `addComponent` (`component-model`) and `addEffect`
(`effect-model`). Those are stubs today; the cases are written against their public signatures and
will land once those areas do.

## Documentation — what the package README must carry

`package-and-exports` owns the user-facing documentation, "carrying the coverage table and a
description of every divergence in it, kept in step with the spec's own table as a condition of any
behaviour change rather than as a later sweep". Planned sections, in order (**not written in this
wave**):

1. **What this is** — a test-double library of in-memory fakes of the `@minecraft/server` object
   model that hold state and mutate it, so a test asserts that health is now 20 rather than that
   `setCurrentValue` was called with 20. One paragraph, plus the problem it answers (the package
   ships declarations with no runtime JavaScript).
2. **Install** — `npm i -D @twin-digital/minecraft-test-lib`, ESM only, one peer dependency on
   `@minecraft/server@2.8.0`, no runtime dependencies, no test-framework dependency.
3. **Getting started** — the `createServer()` + `installMyPack(server)` snippet, with the sentence
   that the second line is the _pack's_ own entry point. Followed by the constraint stated plainly:
   **the library never replaces or intercepts the module import**, so a pack that reaches the engine
   through a bare `import { world } from '@minecraft/server'` is outside its reach.
4. **The bundle** — the ten properties `createServer()` returns, that they are named exactly as the
   module exports them and are assignable to a `Pick<>` of it, and that the eight registries are
   declared and throw.
5. **Free functions** — the spec's twelve-row table verbatim (`createServer`, `createEntity`,
   `createPlayer`, `addComponent`, `removeComponent`, `registerEffectBaseName`, `invalidate`,
   `emit`, `advanceTicks`, `getOutput`, `getTriggeredEvents`, `getHandlerErrors`), with the reason
   they are free functions: a fake exposes no member the real API does not have.
6. **Presets** — `withVanillaDimensions` and `asSpawnedEntity`: what each supplies, that they are
   opt-in and compose, and that neither invents per-type vanilla data. The `xp_orb` simplification
   is named here as well as in the divergence table.
7. **Construction populates nothing** — the resting state, and the difference between the two kinds
   of absence: an unsupplied value throws `UnsetValueError`, an absence the engine can exhibit reads
   `undefined`.
8. **Errors** — the five exported classes, what raises each, and the observed message shapes
   (`InvalidEntityError` with `id`/`type`, `ArgumentOutOfBoundsError`, `InvalidArgumentError`,
   `NotImplementedError`, `UnsetValueError`), plus the plain `Error`s an attribute component and an
   effect throw on an invalid owner.
9. **What a read that finds nothing does** — the five rules, in order, as a numbered list. This is
   the section a reader hits when a fake threw something they did not expect.
10. **Invalidation** — `remove()` versus `invalidate()`, the four members that stay readable, and
    that the guard fires at the call rather than the access.
11. **Coverage** — the spec's full coverage table, reproduced row for row: every behaviour ruled on,
    marked **modelled**, **not modelled** or **divergence**, each divergence row carrying the
    difference itself. Prefaced by the sentence that the table states what the design ruled on and
    nothing more.
12. **Divergences in detail** — a subsection per divergence row, since "someone reading it has the
    library in hand and the spec nowhere near". One short paragraph each, saying what the fake does,
    what the engine does, and the shape of a test that would pass here and fail there:
    fresh-entity components; `minecraft:xp_orb`'s spawn frame; entity id spelling;
    `EntityQueryOptions`' eighteen unhonoured fields; `spawnEntity` placement; post-spawn motion;
    `triggerEvent`; the damage-invulnerability window; projectile damage; `addEffect` on `NaN` /
    `Infinity`; effect duration decay and expiry; `displayName` locale; `displayName` for a custom
    type; after-event dispatch timing; before-event mutable payload fields; a subscriber that
    throws; the tick loop.
13. **Keeping this in step** — one short note that a change to a modelled behaviour is not complete
    until its coverage row says the same thing, and that a `divergence` row with no evidence behind
    it is a row to delete. Case L15 is the mechanical half of this.

## Open items

- **Own-property order.** `FakeEntity`'s constructor assigns `id` before `typeId`, so
  `Object.keys(entity)` yields `['id','typeId']` where the engine yields `['typeId','id']`
  ([[f:entity-shape-is-identical-valid-or-invalid]]). The spec only states the _count_, so G5–G8 are
  planned as count-and-set assertions. Swapping the two assignments in `tools/generate.ts` would
  match the observed order exactly; flagged for `surface-codegen` rather than assumed.
- **`for-in` = 62 depends on `Entity` alone.** The count is the engine's for `Entity`; no fact pins
  it for `Player` or any component class, so G10/G11 are `Entity`-only and G22 asserts the
  enumerability rule rather than a count for other classes.
- **Cross-area stubs.** Sections F, G, H, I and K cannot run until `entity-model` (`createEntity`,
  `createPlayer`, `invalidate`), `component-model` (`addComponent`) and `effect-model` (`addEffect`)
  land.

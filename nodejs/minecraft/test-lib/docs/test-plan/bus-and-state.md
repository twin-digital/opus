# Test plan — event-bus, system-scheduler, persisted-state, output-capture

Every planned case for the four areas, with the assertion it makes and the spec sentence, fact or
decision it comes from. Wave 1: this document only — no tests and no implementation.

**Files.** `src/events.test.ts`, `src/scheduler.test.ts`, `src/persisted.test.ts`,
`src/output.test.ts`, colocated beside the source they cover. The cross-cutting group in §0 lives in
`src/create-server.test.ts`.

**Dependencies on other areas.** Cases marked _(needs entity-model)_, _(needs component-model)_ or
_(needs effect-model)_ assume `createEntity`, `createPlayer`, `invalidate`, `addComponent` and
`entity.addEffect` behave as their owners' specs describe. They are written against those free
functions and will be skipped until those areas land.

**Runtime constants.** `@minecraft/server` ships no JavaScript
[[f:server-package-ships-types-only]], so every enum member a test needs is written as its string
literal with a cast — `'Sidebar' as MC.DisplaySlotId`, `'Entity' as MC.ScoreboardIdentityType`.

Open questions the plan could not settle are collected in §5; every case that rests on a library
ruling rather than a source is marked **[ruling]**.

## 5. Open questions and gaps

These are the places the spec did not settle a testable answer. Each is listed with the ruling the
plan assumes so a reviewer can overturn it in wave 2 before the tests are written.

**5.1 The `HandlerError.signal` format is inconsistent between the state model and the bus.**
`src/runtime/state.ts` documents `signal` as _"the signal whose subscriber threw, as
`afterEvents.entityHurt` names it on the world"_, while `src/events.ts` writes
`` `${scope}.${name}` `` — i.e. `world.afterEvents.entityHurt`. Cases 1.5.6 and 1.5.7 pin the
implemented form (the fully qualified one) because it is the only one that distinguishes
`world.afterEvents.effectAdd` from `world.beforeEvents.effectAdd`. The TSDoc needs correcting.

**5.2 A scheduled callback that throws is unspecified.** The spec's isolation ruling
[[d:handler-errors-are-isolated-and-recorded]] covers event subscribers, not `system.run` callbacks,
and no fact observes the engine's behaviour there. No case is planned. Options: isolate and record
in the same log (needs a `HandlerError.signal` value like `system.run`), isolate and swallow, or let
it propagate out of `advanceTicks`. Propagating is the most honest default and the easiest for a
test author to debug — flagging for a ruling.

**5.3 The scoreboard members the spec does not name.** The spec enumerates `addObjective`,
`getObjective`, `getObjectives`, `removeObjective`, `setScore`, `getScore`, `getScores`,
`getParticipants` and `getObjectiveAtDisplaySlot`. The declarations also carry
`Scoreboard.getParticipants`, `Scoreboard.clearObjectiveAtDisplaySlot`,
`ScoreboardObjective.addScore`, `hasParticipant` and `removeParticipant`. Rule 3 says an unnamed
member throws, so cases 3.4.9 and 3.5.6 plan `NotImplementedError` for all five —
`Scoreboard.setObjectiveAtDisplaySlot` is the exception, since without it the modelled
`getObjectiveAtDisplaySlot` could never answer anything. That reading makes the scoreboard notably
partial (a pack calling `addScore` hits a wall over trivially derivable behaviour); if the intent was
"the scoreboard behaves", these five should be modelled and the cases inverted.

**5.4 An objective added with no display name.** `addObjective(objectiveId, displayName?)` leaves
`displayName` — declared bare `string` — unsupplied, so rule 5 gives `UnsetValueError` (case 3.3.6).
The engine almost certainly defaults it to the objective id, but nothing in the fact pool pins that,
and inventing it would be fabrication. Worth a probe.

**5.5 The lifetime of a removed objective and a removed entity's identity.** `ScoreboardObjective`
and `ScoreboardIdentity` both declare `isValid`, and no fact says what happens to them after
`removeObjective` or `entity.remove()`. Case 3.3.9 rules that a removed objective reads
`isValid === false`; nothing is planned for an identity outliving its entity.

**5.6 Whether `getOutput` returns a snapshot or a live view.** The declared return is
`readonly OutputRecord[]`; `src/runtime/state.ts` holds the log as a mutable array. Case 4.13 is
written to pass under either reading. A ruling would let it be tightened.

**5.7 The default `tickDelay` and `tickInterval`.** Both are declared optional
(`runTimeout(cb, tickDelay?)`, `runInterval(cb, tickInterval?)`) and the spec states the semantics
only for the explicit form. No case is planned for the omitted form. `1` is the obvious reading —
`runTimeout(cb)` becoming `run(cb)` — but it is a library ruling either way.

**5.8 A negative or fractional `advanceTicks` count.** Unspecified; no case planned. A negative count
must not run `currentTick` backwards.

**5.9 `system.currentTick` and the `advanceTicks` contract.** `advanceTicks` takes `ServerLike`
(`Pick<FakeServer, 'world'>`), so it reaches `ServerState` through the world; `system` is not a
parameter. Every scheduler case therefore constructs the server and passes it whole, which is what
the spec's examples do anyway. No change needed — noted so a reader does not expect
`advanceTicks(system, n)`.

**5.10 Signal payload construction for `emit`.** The library ships no payload builders, so cases
1.3.x, 1.7.6 and 1.8.7 hand-write object literals cast to the declared payload type. This is
[[d:every-signal-exists-few-are-raised]]'s named falsifier ("tests routinely need a payload built for
them"); worth watching as the test suite grows, but not a blocker.

**5.11 State-model additions needed.** `ServerState` has no counter for scoreboard identity `id`
numbers (case 3.6.1 requires one) and no registry of identities outside per-objective
`ObjectiveState.participants` — a `ScoreboardIdentity` must exist before any objective scores it, for
`entity.scoreboardIdentity`. Both are fields `persisted-state` will add in wave 2.

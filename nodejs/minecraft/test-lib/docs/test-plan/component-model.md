# Test plan — component-model

Planned cases for `src/components.ts`: `addComponent` / `removeComponent`, `getComponent` id
normalization, the seven attribute-shaped components, and every cascade that writes health — the
component writes, `applyDamage`, and `kill()`'s health-bearing branch. Tests land in
`src/components.test.ts`.

Each case gives the vitest name (`describe` > `it`), what it asserts concretely, and the spec
sentence or fact it comes from. Cases marked **[inference]** assert behaviour the spec does not
pin; they are listed so the ruling is visible and reviewable rather than buried in the
implementation. Cases marked **[gap]** additionally need a ruling before they can be written as
stated — see _Open questions_.

Fixtures assumed throughout: `const server = createServer()`, `const entity = createEntity(server,
{ typeId: 'minecraft:sheep' })`, and a `record(server)` helper that subscribes to
`world.afterEvents.entityHurt`, `entityHealthChanged` and `entityDie` (and
`world.beforeEvents.entityHurt` where a case needs it) and returns the delivered payloads in
delivery order, so an "event order" assertion is one `expect(...).toEqual([...])` over a list of
`{ signal, … }` records. Health-bearing entities are staged with `addComponent(entity,
'minecraft:health', [0, 8])` — `currentValue` 8, `effectiveMin` 0, `effectiveMax` 8 — which is the
`8/[0, 8]` shape every damage fact was observed on.

**Total planned cases: 140.**

## How `kill()`'s two halves meet

`kill` is registered **once**, by `component-model`, on `Entity` and `Player` (a single
`ClassBehaviour` entry, since `registerBehaviour` merges per class and two modules registering the
same member name would silently overwrite one another). The registered body:

1. looks up the attached `minecraft:health` component;
2. with one, runs the health-bearing cascade above and returns `true`;
3. with none, calls a function `entity-model` exports for the health-less branch — proposed
   `killWithoutHealth(entity: MC.Entity): void`, which fires `entityDie` with cause `selfDestruct`
   and nothing else — then returns `true`.

That keeps `entity-model`'s half testable on its own and leaves one owner for the member
registration. entity-model's tests cover the no-health branch (`kill()` on a component-less entity
returns `true` and fires only `entityDie`, [[f:kill-no-health-behaviour]]); this plan's I-series
covers the health-bearing branch and the second-call case. Note the engine's health-less `kill()`
also invalidates the reference synchronously, which the spec's _Entities_ section rules out for the
fake ("`kill()` … never invalidates") — that divergence is entity-model's to state.

## Open questions

Each of these blocks or qualifies a planned case. None is a spec contradiction; each is a place the
spec does not rule.

1. **Unknown component id.** `addComponent(entity, 'minecraft:not_a_component')` and
   `getComponent` of one. `getComponent` most likely reads `undefined` under rule 4, but
   `addComponent` has no mapping to construct a fake from and no stated error. No test is planned
   until this is ruled on.
2. **Re-attaching an already-attached id** (A13) — replace, or throw.
3. **Attaching or detaching on an invalidated entity** (A14) — the stub says "live entity"; the
   error class is not pinned.
4. **What detachment does to a held component reference** (B6, B7) — the fake almost certainly goes
   invalid, but which guard shape its members then take is a library ruling, not an observation.
5. **A no-op health write** (G9) — whether `setCurrentValue` to the value already held still fires
   `entityHealthChanged`.
6. **Whether `applyDamage` raises the `entityHurt` before-event for a non-admitted amount**
   (H12/H13). Planned as "fires nothing at all", which reads "change nothing" strictly.
7. **`UnsetValueError` versus the admission boolean** (H34, H35): with health attached but no
   values, does `applyDamage` throw, or return its admission boolean first? Planned as throwing,
   since the boolean is settled but the write cannot proceed.
8. **`kill()`'s `entityHurt` damage on a non-zero `effectiveMin`** — "damage equal to current
   health" is exact only where the minimum is zero (`current − effectiveMin` is equally consistent
   with the 8/[0,8] observation), and [[f:reaching-effective-minimum-is-fatal]] found no vanilla
   type with a non-zero minimum. No case asserts the value in that configuration.

## Not turned into a test

- **`entityHurt` handler isolation and `getHandlerErrors`** during a damage cascade
  ([[f:throwing-handler-is-isolated]]) — event-bus owns it; this plan assumes dispatch already
  isolates.
- **After-event deferral** — the fake dispatches synchronously by design
  ([[r:synchronous-event-delivery]]); the divergence row is event-bus's.
- **The five events observed in `remove()`'s window** ([[f:kill-and-remove-cascades]]'s caveat) —
  the fact itself says to read them as observed, not as a cascade to reproduce, and `remove()` is
  entity-model's.
- **Per-type vanilla component data** (a sheep's fourteen components, its 8/8/0/8 health) — the
  Coverage row rules it not modelled, so there is nothing to assert beyond C4's empty
  `getComponents()`.

# Test plan — effect model

Covers `src/effects.ts` and the shipped display-name table (`src/effect-names.ts`): `addEffect`,
`getEffect`, `getEffects`, `removeEffect`, the amplifier-first replacement rule, non-decaying
durations, `Effect.displayName` with its shipped bases and computed numeral,
`registerEffectBaseName`, and the effect members on an invalid owner.

Tests are colocated as `src/effects.test.ts` and `src/effect-names.test.ts`. Every case below names
the `describe` > `it` it will read as, what it asserts, and where in the settled spec or the fact
pool it comes from.

Out of scope here: entity lifecycle, components, damage, scheduling (`advanceTicks` is used, not
tested), persisted state, output, presets.

**89 planned cases.** Ten of them are `it.each` tables; the display-name walk is the largest, 37
rows × 7 amplifiers.

---

## Notes, gaps and things deliberately not tested

1. **`addEffect` accepting an `EffectType` object.** The declaration is
   `addEffect(effectType: EffectType | string, …)`, but every member of the `EffectTypes` registry
   throws `NotImplementedError` `[[d:registries-are-declared-and-throw]]`, so a test cannot obtain
   an `EffectType`. The spec says nothing about the object arm. No case planned; the implementation
   should decide and record it (reading `getName()` is the obvious answer).
2. **`EntityEffectOptions.showParticles`.** Declared, and nothing in the spec reads it. Case 4 only
   uses it to prove it does not disturb the amplifier default. No behaviour asserted.
3. **`removeEffect` bare-id tolerance (case 54) is extrapolated.** The prefix-tolerance probe covers
   `addEffect`, `getEffect`, `spawnEntity`, `getComponent` and `triggerEvent`, and the spec's own
   sentence lists only the first four. `removeEffect` is unobserved. The plan takes the tolerant
   reading for symmetry with `getEffect`; if the implementation goes the other way, this case flips
   and the choice belongs in the Coverage record as the library's own.
4. **The return of a refused re-add (case 33) is unobserved.** The probe recorded the return only
   for the add and the replacing update. "The resulting `Effect`" reads most naturally as the
   surviving effect. Flagged rather than assumed silently.
5. **Case 31 pins a real divergence in the replacement comparison.** The spec says the two bases
   "coincide here" — true only while no ticks pass between the base add and the re-add. Once
   `advanceTicks` runs, they part: the engine would replace a 400-duration effect with a 320-duration
   re-add (320 > 250 remaining), while the fake refuses it (320 < 400 stored). The Coverage table
   carries a decay divergence row but does **not** carry a row for the replacement comparison
   parting from the engine after ticks advance. That is a Coverage gap worth raising.
6. **`effectAdd.effectType` carrying the display name (cases 59–62) rests on probe log lines, not on
   a fact's `claim`.** The claim text of `[[f:before-event-field-writes-take-effect]]` is about
   `duration`; `effectType="Speed II"` appears only in its quoted handler notes, identically in 3/3
   runs and in the cancelled-return probe. The spec's justification for `registerEffectBaseName`
   being world-keyed only makes sense on this reading. Consequence for the implementation: the
   payload's `effectType` must be a **lazy getter**, or `addEffect` on an unregistered custom type
   would throw `UnsetValueError` merely by constructing the payload, even with no subscriber.
7. **Case 65 (a handler writing an out-of-bounds duration) is unobserved.** The bounds check is
   argument validation and the probe only wrote in-range values. The plan takes "the write is
   honoured" `[[f:before-event-field-writes-take-effect]]` at face value and does not re-check
   bounds; if the implementation re-checks, this case flips.
8. **No state-model change is needed.** `ServerState.effectBaseNames`, `EntityData.effects` and
   `EffectState` (with its `present` flag) already carry everything this area needs, and
   `guard-data.json` already holds the effect guard table.
9. **Locale.** Only the observed locale's strings exist. Case 84 covers the documented escape hatch;
   no case asserts anything about another locale's numeral placement, which the Coverage row leaves
   open.

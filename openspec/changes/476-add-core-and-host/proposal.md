# Proposal

## Why

Wishem has a blueprint and no code. Each later change needs a core that holds a model and gives that model to the code that uses it, such as a host, a renderer, or an agent. This change builds the first core and the first host, so that the [first workbench UI slice](https://github.com/twin-digital/opus/issues/477) can add a page on a working base.

## What Changes

- Add three packages in `nodejs/wishem/`, with the npm scope `@thrashplay`:
  - `@thrashplay/wishem-core` in `core`: the model data types, the validation of the structure of a model, the snapshot, and the read operations of the interface of the core.
  - `@thrashplay/wishem-host-nodejs` in `host-nodejs`: the `wishem start` command, the read and the watch of a model folder, and the local HTTP port.
  - `@thrashplay/wishem-workbench` in `workbench`: the model of the base workbench.
- Define the file format of a model folder. A definition is data, not code:
  - `definitions/<id>.json` holds one component type.
  - `state.json` holds the authored state.
  - A component type, a field, and an entity each have an ID that does not change. The ID is a UUID. A component type and a field each have a label that can change.
  - The authored state refers to a component type and to a field by ID.
- Give the snapshot as one JSON document that holds the definitions and the authored state:
  - `GET /snapshot` returns the current snapshot.
  - `GET /snapshots` is a stream of Server-Sent Events. It sends the full snapshot at the start and after each change.
- Report a problem in the model files in the terminal of the start command. The core continues to give the last correct snapshot. The command does not start with a model that is not correct.
- Add the first model: one component type with the label `AppBar`, which has one field with the label `title`, and one entity.
- Update the Wishem blueprint for the items that this change settles: definitions as data, the ID and the label of a component type and of a field, the packages, the npm scope, and the transport of the snapshot.

Not in this change: a page, a renderer, a view, the link between a view and a component type, a second core, the write, time, and input operations, live state, steps, behaviors, and the agent.

## Capabilities

### New Capabilities

- `wishem/core/model`: the data of a model, the IDs and labels, and the rules that make a model correct.
- `wishem/core/snapshot`: what a snapshot holds, and how a core gives the current snapshot and each later snapshot to the code that uses it, such as a host or a renderer.
- `wishem/host-nodejs/model-folder`: how the Node.js host stores a model as files in a model folder.
- `wishem/host-nodejs/start-command`: the command that starts a core for a model folder, watches the folder, serves the snapshot on a local port, and reports problems.

### Modified Capabilities

None. No Wishem specification exists.

## Impact

- New packages: `@thrashplay/wishem-core`, `@thrashplay/wishem-host-nodejs`, `@thrashplay/wishem-workbench`. The three packages are private in this change.
- No new third-party dependency. The host uses `node:http`, `node:fs`, and `node:util`.
- `README.md` package list and repo-kit config: regenerated by `pnpm sync` and `pnpm update-readme`.
- Blueprint files in `nodejs/wishem/docs/`: `glossary.md`, `concepts.md`, and `rules.md`.
- Issues #477, #478, and #479 start from the file format and the snapshot of this change.
